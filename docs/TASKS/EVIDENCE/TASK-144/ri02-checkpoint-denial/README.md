# R-I02 — checkpoint refusal before success decoding

The deployed checkpoint contract has early `resource_exceeded` and `invalid_baseline` envelopes without `catalog`, `prices`, `history`, `images`, or `integrity`. iOS decoded the complete success DTO first, losing the actual refusal to `keyNotFound(catalog)`. The authenticated Android observation and read-only TEST preflight established this shared contract branch. The iOS device's separate sign-in persistence/discovery issue occurs earlier and is not attributed to this decoder.

Two fixtures were constructed with the deployed PostgreSQL helper, using synthetic identities and event fences. Their aggregate resource preflight matches the observed TEST branch (native PostgreSQL compressed history requiring external remediation). The fixture bytes are shared with Android. Tests preserve the envelope and bind its synthetic identity to each isolated local scope. No server/data remediation, real credentials, or impersonation is involved.

The fix reads a strict envelope, validates schema/shop/account/device and any expected baseline scope fence, then handles the status. Only `ready` reaches the unchanged full DTO and all existing success checks. Stable refusals yield bounded safe codes: `checkpoint_resource_exceeded`, `checkpoint_invalid_baseline`, `checkpoint_integrity_blocked`, or `checkpoint_status_unsupported`. The convergence marker uses equivalent `convergence_marker_*` codes and additionally verifies the complete expected baseline scope before interpreting status. Unknown raw status text is not echoed. Missing status and truncated ready bodies still fail decoding; no success defaults were added.

The existing atomic recovery loop retries only `checkpointChanged`. Integration regressions verify each refusal makes one checkpoint request, downloads no pages, activates no generation, and preserves binding and durable journal bytes. Future explicit recovery invocations remain possible after external remediation.
